# ChatGal 本地推理引擎（拆分方案）

> 状态：**方案已定、本体已拆完、引擎 App 尚未实现**（2026-09-17）
> 本文记录技术路线、接口形状、引擎侧的实现细节与踩过的坑。真要开工时照这份走。

---

## 1. 为什么拆

端侧推理需要两套 native 库：

| 库 | 用途 | 体积 |
|----|------|------|
| llama.cpp（`libllama.so` / `libggml*` / `libggml-vulkan.so`） | 跑 GGUF | ≈ 33 MB |
| LiteRT-LM（`libLiteRtLm.so` + 加速器 + Gemma 约束库…） | 跑 `.litertlm`，**手机 GPU/NPU 加速走这条** | ≈ 55 MB |

放在本体里的实际代价：**APK 94.1 MB → 198.4 MB**。

拆出去之后：

| | 体积 | 内容 |
|---|---|---|
| **ChatGal（本体）** | **94.1 MB** | 内容包 72 MB + UI/引擎壳 ≈ 22 MB |
| **ChatGal 本地推理引擎**（待做） | ≈ 110 MB | 两套 native 库 + 权重管理 + HTTP 服务 |

附带好处：引擎可以单独更新（换 native pin、加后端都不用重发本体）、可以给别的 App 复用、不想用本机推理的人根本不用装。

## 2. 架构

```text
┌─ ChatGal 本地推理引擎（独立 App）────────────────────────┐
│  Flutter + llamadart（与本体原先同一套栈）                │
│  ├─ 模型管理：档位表 / 下载器 / 进度 / 删除                │
│  ├─ 推理：LocalLlamaProvider（GGUF ↔ llama.cpp，           │
│  │        .litertlm ↔ LiteRT-LM，失败自动回落 CPU）        │
│  └─ HttpServer（Dart 内置，无需 native server）            │
│       暴露 OpenAI 兼容端点 → 调用上面的 provider           │
│  Android 侧：前台服务 + 常驻通知（保活，见 §5）            │
└───────────────────────┬──────────────────────────────────┘
                        │  http://127.0.0.1:<端口>/v1
                        │  （同设备 App 之间的 TCP 是通的，无需权限）
┌───────────────────────┴──────────────────────────────────┐
│  ChatGal（本体）—— **零改动**                              │
│  就是个普通的 OpenAI 兼容供应商：地址填 127.0.0.1:<端口>/v1 │
│  「模型供应商」页现成支持                                   │
└──────────────────────────────────────────────────────────┘
```

**关键点：本体不需要为这件事写任何代码。** 它能连任何 OpenAI 兼容服务，本机引擎只是其中一个地址。这也是为什么本体可以先拆完、引擎以后再补 —— 两边互不阻塞。

## 3. 引擎侧要暴露的接口

最小可用集合（本体只需要第一个）：

| 端点 | 用途 |
|------|------|
| `POST /v1/chat/completions` | 本体唯一需要的；返回 `{choices:[{message:{content}}]}` |
| `GET /v1/models` | 「模型供应商」页会拉一次，用于下拉选模型 |
| `GET /health` | 可选，给引擎自己的界面/诊断用 |

请求体按 OpenAI 走，**但注意两个只能在这里处理的点**：

1. **`stream: false`**：本体当前是非流式（`OpenAiCompatibleProvider` 就是 `stream=false`），引擎可以先只实现非流式。
2. **`messages` 的顺序与角色**：本体发的是 `system` / `user` / `assistant` 三种，直接透传给 llamadart 的 `LlamaChatMessage.fromText(role:, text:)`。

端口：固定一个不常用的（如 `8080` 或 `18080`），并且**只绑 `InternetAddress.loopbackIPv4`**（不要 `anyIPv4`，否则同一 Wi-Fi 下别的设备也能连进来）。

## 4. 引擎侧的实现细节（都是实测踩出来的）

### 4.1 llamadart 的两条通路不能共用参数

```dart
// GGUF（llama.cpp）
ModelParams(
  contextSize: 4096,
  preferredBackend: GpuBackend.cpu,      // 或 vulkan
  gpuLayers: ...,
  flashAttention: ...,
)
// .litertlm（LiteRT-LM）—— **只给这一项**
ModelParams(
  contextSize: 4096,
  liteRtLmBackend: LiteRtLmBackendPreference.gpu,   // gpu / npu / cpu
)
```

**不要**给 `.litertlm` 传 `preferredBackend` —— llamadart 的文档写着它"会被当作 LiteRT-LM 的自动提示"，传 `GpuBackend.vulkan` 会把 LiteRT 也带进 Vulkan 那条路（实测掉到 0.3 token/s）。

### 4.2 native runtime 的 pin 与开关都写在 pubspec 的 hooks 段

```yaml
hooks:
  user_defines:
    llamadart:
      llamadart_native_tag: v0.4.1          # v0.4.0 不认 Spark 的 spark2_5 架构
      # llamadart_native_runtimes: llama_cpp  # 只打 llama.cpp（会去掉 LiteRT）
```

- **`--dart-define` 传不进 hook**（连 `flutter clean` 都没用）—— 必须是 pubspec 这一段。
- LiteRT 那套库的 `requiredLibraries` 要求**整套齐全**，少一个文件初始化就失败。要裁剪只能整套不要（`llamadart_native_runtimes: llama_cpp`），不能挑着删。

### 4.3 Spark-X2.5 必须关掉 thinking

它的 chat template 里 `enable_thinking` **默认 true**：不显式关掉会先跑一段 `<think>`，
实测同一句话 **0.9s → 4.0s**（输出看着一样，白烧四倍时间）。

```dart
engine.create(messages, params: ..., enableThinking: false)
```

### 4.4 两条路的性能特征完全不同（同一台机器实测）

| 配置 | 生成速度 |
|------|----------|
| Spark-X2.5-1.7B Q4_K_M + llama.cpp + CPU | 7.3 token/s |
| Gemma 4 E2B + LiteRT-LM + CPU（XNNPACK） | 19.5 token/s |
| Gemma 4 E2B + LiteRT-LM + **GPU**（ML Drift） | **25.9 token/s** |
| 同上 + NPU 后端 | 1.4 token/s（该机器的 NPU 委托反而不行） |

- **GPU 加速靠 LiteRT-LM**，与 llama.cpp 无关：llama.cpp 在移动端的加速路径是 OpenCL 与 Hexagon NPU，官方对此的优化只覆盖 `Q4_0`，而 llamadart 不带这两条后端，只有 CPU / Vulkan —— 实测 **Vulkan 在 Adreno 上比 CPU 慢数倍**。
- 官方 benchmark（骁龙 8-Elite 级、1080 预填充 / 256 解码）是 CPU 46.9 / GPU 52.1，方向一致，绝对值高一些。
- 引擎里应该把这两条路**都提供**，并在界面上写明各自适合什么。

### 4.5 权重来源

| 档位 | 仓库与文件 | 大小 |
|------|-----------|------|
| Spark-X2.5-1.7B（Q4_K_M / Q4_0）、4B（Q4_K_M） | `XHToken/Spark-X2.5-*-GGUF`、`Mungert/Spark-X2.5-1.7B-GGUF` | 1.06 / 0.92 / 2.42 GB |
| Gemma 4 E2B（LiteRT） | `litert-community/gemma-4-E2B-it-litert-lm` → `gemma-4-E2B-it.litertlm` | 2.42 GB |

- 全部**非 gated**，直链 + `hf-mirror.com` 镜像都实测 200（Google 官方那份 `google/gemma-3n-*` 是 `gated=manual`，应用内下不了）。
- 下载器要支持：主源失败自动切镜像、Range 续传、`.part` 完成后改名、可取消。
- 换权重来源后要清理**孤儿权重**（界面上已没有入口能删的那种）。

### 4.6 测试/自检要躲开这些测量陷阱

引擎需要一个「试跑一次」的自检按钮，但**别重犯这几个错**（每一个都让速度数字失真一个数量级）：

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 chunk 数当 token 数 | LiteRT 会把多个 token 合并成一个 chunk，15 tok/s 被报成 1.6 | 生成后问引擎要真实 token 数（`engine.getTokenCount(text)`） |
| 把加载算进生成 | LiteRT 的 `loadModel` 只花 10ms（只是登记），真加载在**首次推理**时 | 先预热一次，再计时 |
| 样本只有 1~2 个 token | 那点耗时几乎全是固定开销（预填充/调度） | 让模型写一段长文本（≥150 token）再测 |
| 只测一个后端 | NPU/GPU 可能本来就不可用 | 三个后端各测一次，并**标明实际用的哪个** |

## 5. Android 侧的保活（这条是本方案最大的风险）

本体切回前台后，引擎 App 就进了后台 —— 系统会在几分钟内冻结它，**推理请求直接超时**。
所以引擎必须跑一个**前台服务**：

- `AndroidManifest.xml`：`<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>`
  （Android 14+ 还要选类型，如 `FOREGROUND_SERVICE_SPECIAL_USE` 或 `..._DATA_SYNC`，并申请对应权限）
- 一个常驻通知：「ChatGal 本地推理引擎运行中 · 端口 8080」
- `MainActivity` 暴露 MethodChannel（如 `chatgal_engine/service`）的 `start` / `stop` / `isRunning`
- Dart 侧用 `MethodChannel` 启停；App 启动时若「上次是开着的」就自动恢复

**这些只能在真机上验证**：通知是否常驻、系统会不会在息屏后掐掉 socket、切后台多久开始拒绝连接。
开发机上一条都测不出来 —— 所以这一步一定要安排真机实测，别只靠代码审查。

> 另一种更省事的思路：**不做前台服务**，改用「引擎 App 一直开着（前台）才可用」。
> 体验差但实现简单，可以先这样出一版验证推理链路，再补保活。

## 6. 本体侧的现状

- 设置 → **本地模型** 仍然保留入口，点进去是一页说明（怎么装引擎、怎么把地址填进「模型供应商」），并带一个「去模型供应商配置」的按钮。
- 本体的「模型供应商」通路**不需要任何改动**：新增一条供应商、Base URL 填 `http://127.0.0.1:<端口>/v1`、API Key 随便填（本地服务不校验）即可。
- 内网/局域网也可以用同一套接法：把引擎装在电脑上跑（`llama.cpp` 的 server 或 Ollama 都行），本体填 `http://<电脑IP>:<端口>/v1`。

## 7. 开发过程中踩过的坑（按时间顺序，都别再犯）

1. **为了省 55 MB 把 LiteRT 的 native 库从 APK 里剔掉** —— 等于亲手关掉手机上唯一能用 GPU 加速的路径。判据应该是"能不能用"，不是"看起来用不到"。
2. **把 llama.cpp 的参数传给 LiteRT 模型**（`preferredBackend`）—— 被当作 LiteRT 的提示，把 LiteRT 带回 Vulkan。
3. **拿 chunk 数当 token 数报速度** —— 数字直接失真一个数量级。
4. **把 LiteRT 的隐式加载算进生成时间** —— `loadModel` 只有 10ms，真加载在首次推理。
5. **测试 prompt 写"只回一个词"** —— 样本 1 个 token，测的是固定开销不是吞吐。
6. **UI 文案里用 markdown 粗体** —— Dart 界面会原样显示 `**`。

以及一条方法论上的教训：**在没有可靠测量之前不要下结论**。上面第 3~5 条让好几轮"诊断"都建立在假数字上，
而真正让问题暴露的是**设备日志**（`loadModel` 只花 10ms、输出只有 1 个 token 这些事实都在日志里）。
